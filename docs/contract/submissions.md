# Submission API contract — version 1

This file specifies `POST /labs/{labId}/submissions`. Contract tests must check the implementation against it. Change the contract separately, with a reason, before changing its behavior.

The [class project brief](../LeeTKOB%20%E2%80%94%20class%20project%20brief.md) is authoritative. This contract makes explicit team choices for endpoint details the brief leaves open; it does not rely on a product-owner FAQ answer.

## 1. Conventions

- Requests and successful responses use UTF-8 JSON. Error responses use `application/problem+json`.
- JSON object member names must be unique. Duplicate names are malformed JSON for this endpoint.
- IDs are UUID strings. Timestamps use RFC 3339 UTC, such as `2026-11-11T12:00:00Z`.
- Clients ignore unknown response fields. Requests containing unknown body fields are rejected.
- Source code is a JSON string containing the student's C++ submission. The server preserves it exactly after JSON decoding.

## 2. Errors

Every error response for this endpoint is an RFC 9457 problem details object:

```json
{
  "type": "https://leetkob.example/problems/invalid-request",
  "title": "Invalid request",
  "status": 400,
  "detail": "The source field is required."
}
```

`type` is the stable identifier in the table; `status` equals the HTTP status. `detail` describes the occurrence without exposing credentials, source code, stack traces, SQL, or internal paths. Clients branch on `type`, not `detail`. The example domain is an identifier; it need not be reachable.

| Type suffix (`https://leetkob.example/problems/…`) | Status | Title | When |
|---|---:|---|---|
| `unauthenticated` | 401 | Authentication required | The session is missing, invalid, or expired. |
| `forbidden` | 403 | Forbidden | The authenticated user is not a student. |
| `invalid-origin` | 403 | Invalid origin | The `Origin` header is missing or does not match the configured application origin. |
| `not-found` | 404 | Lab not found | The lab ID is invalid, the lab does not exist, or the student is not enrolled. |
| `invalid-idempotency-key` | 400 | Invalid idempotency key | The key is missing, empty, or outside the allowed format. |
| `unsupported-media-type` | 415 | Unsupported media type | The request is not `application/json`. |
| `payload-too-large` | 413 | Payload too large | The request body exceeds the limit. |
| `invalid-json` | 400 | Malformed JSON | The body is not valid UTF-8 JSON, including multiple JSON values. |
| `invalid-request` | 400 | Invalid request | The JSON object fails the field rules. |
| `idempotency-key-in-flight` | 409 | Request in progress | A matching key is currently being processed. |
| `idempotency-key-reused` | 422 | Idempotency key reused | A completed key is reused with a different request. |
| `unavailable` | 503 | Service unavailable | The submission and its job cannot be durably recorded. |
| `internal` | 500 | Internal error | An unexpected server error occurs. |

## 3. Resources

**Submission**, returned immediately after creation:

```json
{
  "id": "c6b47c2f-71b4-4de1-acbb-6e0d8692949c",
  "labId": "7a8fdf2f-91fb-4c10-881d-e3d8d7701eca",
  "status": "queued",
  "createdAt": "2026-11-11T12:00:00Z"
}
```

- `id` identifies the submission; `labId` identifies its lab.
- `status` is `queued` in the creation response; judging occurs asynchronously.
- The authenticated student owns the submission. The response does not contain the source or student identity.

## 4. Endpoints

### `POST /labs/{labId}/submissions`

An authenticated student enrolled in the lab submits C++ source code. The server derives ownership from the session; clients cannot choose an owner.

**Request headers**

| Header | Rule |
|---|---|
| `Content-Type` | `application/json`, optionally with UTF-8 charset. |
| `Idempotency-Key` | 1–128 ASCII letters, digits, hyphens, or underscores; generated by the client for one intended submission. |
| `Cookie` | The opaque server-managed session cookie issued by a successful `POST /auth/login`; clients should retain and resend it with a cookie jar. |
| `Origin` | Exactly the configured application origin, including scheme, host, and port. |

**Body:** At most 256 KiB of UTF-8 JSON bytes.

```json
{ "source": "#include <iostream>\nint main() { return 0; }\n" }
```

| Field | Rule |
|---|---|
| `source` | Required, nonempty string; at most 128 KiB when encoded as UTF-8. |

Only the `source` field is allowed. Whitespace-only source is accepted. Compilation errors are judging results, not request validation errors.

**Success:** `201 Created`, `Content-Type: application/json`, and the Submission resource above. This response means the submission and its judging job were durably recorded together; it does not mean the code compiled or passed tests.

**Check order:** session; role; origin; lab ID and enrollment; key; content type; body size; JSON syntax; existing key; body field rules; creation. Stop at the first failing stage. A problem response uses the type in section 2. Configure the application origin separately for each deployment; the server must not derive the allowed origin from the request.

**Idempotency**

- Scope a key to the authenticated student and lab. Keep a successful key for at least 24 hours after creation.
- Compare decoded JSON values, including all fields; object key order and whitespace outside strings do not matter. Source contents, including whitespace and line endings, do matter.
- Same key and same request after success: replay the stored `201` response body and add `Idempotent-Replayed: true`. Do not create another submission or job. The initial response omits this header.
- Same key and different request after success: return `422 idempotency-key-reused`; create nothing.
- If a request with the same scoped key is still processing, return `409 idempotency-key-in-flight`. The client may retry the same request and key.
- Only successful `201` results are retained. After a confirmed rollback, a retry with the same key may be processed again. If a response is lost or a commit outcome is uncertain, the client retries the same request and key; the server checks persisted state before creating anything.
- Commit the submission, durable job, key, request fingerprint, and stored success response atomically. A confirmed rollback creates none of them; an uncertain commit outcome may have committed all of them.
- After the retention period expires, a key may be treated as new. Clients must not rely on deduplication after 24 hours.

## 5. Versions and changes

This is the first published contract; there is no legacy endpoint. Additive response fields may be introduced without a new version. Changes to existing field meanings, validation, access, errors, or retry behavior are breaking changes: publish a new version and document its migration and retirement schedule before retiring this contract. Any change to this file requires a separate change explaining why and corresponding contract tests.
